# 4. 미니게임 카탈로그 운영 / 지속 검수

## 원칙
**대량 생성 → 스펙화 → ASTRA → FABLE → 실제 사람 리뷰 → 선별 유지.**
생성은 넓게, 사용 가능한 풀은 엄격하게 관리한다. 사람에게 모든 저품질 후보를 그대로 떠넘기지 않는다.

카탈로그는 [INDEX](catalog/INDEX.md)를 진입점으로 하며 계속 추가·삭제·수정한다. 원대화 전체 아이디어 목록은 백로그 확정도 출시 약속도 아니다.

## 운영 구조
- 새 후보는 배치 ID와 [게임 스펙](templates/GAME-SPEC.md)을 갖고 수집한다. 최소 분류조차 없는 메모는 정식 카탈로그에 등록하지 않는다.
- 중복·채팅으로 불가능·종료 조건 부재 등 명백한 문제를 먼저 분류한다.
- 활성 목록에는 검토할 후보와 유효한 포맷만 요약한다. 보류/폐기는 이유와 재검토 조건을 짧게 남긴다.
- 상세 폐기 스펙은 archive로 이동하거나 삭제 가능하다. ID와 폐기 이유는 기록해 같은 안의 반복 생성을 줄인다.
- 한 게임의 상세 스펙을 원본으로 삼고 INDEX는 같은 변경에서 갱신한다. 서로 다른 두 곳에 독립적인 룰을 쓰지 않는다.

## 상태 규약
진행 단계: `candidate → astra_passed → fable_passed → human_testing → approved`.
어느 단계에서든 `hold` 또는 `rejected`로 이동할 수 있다.
- candidate: 분류·초안이 있는 검수 전 후보.
- astra_passed / fable_passed: 해당 버전의 검토 기록이 있음. 출시 승인이 아님.
- human_testing: 플레이 가능한 버전으로 사람 검증 중.
- approved: 해당 버전·플랫폼·인원·관계 범위에 QA 증거가 있고 출시 가능한 상태.
- hold: 정보 부족 또는 수정 대기. 필요한 조치를 기록.
- rejected: 현재 안을 폐기. 원인 또는 중복 원본 ID 기록.

사용자의 “살림 / 보류 / 폐기” 중 **살림은 계속 검토할 가치가 있다는 뜻**이다. QA를 통과했다는 뜻으로 번역하지 않는다. 구현 상태는 별도 필드로 관리한다.

## 선별 기준
채팅만으로 성립하는가, 짧게 설명 가능한가, 첫 판부터 참여할 수 있는가, 모두 할 일이 있는가, 끝나는가, Reveal이 플레이와 연결되는가, 재플레이에서 변주가 있는가를 본다.
설명 30초 안쪽은 초기 목표이며 검증된 결과가 아니다. AI 사용 이유가 빈약하거나 기존 게임 이름만 바꾼 안은 보류/수정/폐기 후보로 둔다.

3명 지원 게임은 3명에서 별도 검증한다. 다수결·숨은 역할·짝·팀전이 뻔해지거나 불가능해지는 문제를 확인한다. friends/both 태그만으로 사회적 적합성이 입증되지는 않는다.

## 변경 관리
룰·인원·태그·AI 판정·시간·Reveal의 동작을 바꾸면 버전을 올린다. 영향받는 검수를 다시 수행하고 현재 승인에서 제외한다. 이전 승인과 결과는 이전 버전에 보존한다. 단순 오탈자는 재검수 없이 변경 이력만 남길 수 있다.

게임팩도 별도 버전과 구성 게임 버전을 고정한다. 개별 통과만으로 팩의 총길이·전환·피로도·반복·소외가 검증되었다고 보지 않는다.
